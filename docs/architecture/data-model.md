# Data Model

Schema source of truth: `packages/db/prisma/schema.prisma`.

## Tables

| Table                                    | Purpose                                                                                        |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `users`                                  | Single seeded account (see ADR-0005).                                                          |
| `artists`                                | Canonical + normalized name, used for dedup; optional `musicbrainz_id`.                        |
| `albums`                                 | Belongs to an artist; partial release dates.                                                   |
| `songs`                                  | Belongs to a primary artist + optional album; partial release dates.                           |
| `song_artists`                           | Extra artist roles on a song (featured, producer, ...).                                        |
| `song_user_data`                         | Per-user rating, favorite, note, status, discovery info, `energyLevel`.                        |
| `tags`                                   | Controlled vocabulary: genre, theme, mood, dance, usage, language (see ADR-0007).              |
| `song_tags`                              | Song ↔ tag join, with `source` (user/AI/import/provider) and optional `confidence`.            |
| `audit_events`                           | Append-only log of every mutation (see ADR-0004).                                              |
| `import_jobs`                            | CSV import state: `PENDING` → `ANALYZED` (preview) → `COMMITTED`.                              |
| `memories`                               | A personal memory attached to any entity (`entityType`/`entityId`, no FK).                     |
| `festivals`                              | Festival/event; partial start/end dates.                                                       |
| `festival_performances`                  | Artist ↔ festival join: stage, times, priority, attended, personal rating/note.                |
| `playlists`                              | Internal collection, optionally linking to an external playlist.                               |
| `playlist_items`                         | Ordered song ↔ playlist join with a free-text `reason`.                                        |
| `external_links`                         | Polymorphic link (Spotify/YouTube/Bandcamp/SoundCloud/MusicBrainz/website), with `verifiedAt`. |
| `song_analyses`                          | Versioned AI/manual analysis; `status` DRAFT → APPROVED/REJECTED (never edited in place).      |
| `prompt_versions`                        | Named, versioned system prompt text; one `active` version per name.                            |
| `conversations`, `conversation_messages` | Reserved for a future in-app chat UI — schema only, nothing writes to these yet.               |

## Notable modeling decisions

- **UUIDs everywhere**, generated by Postgres (`gen_random_uuid()` via `pgcrypto`), never
  sequential IDs.
- **Duplicate detection, not prevention**: `normalized_name`/`normalized_title` are indexed but
  not uniquely constrained on `artists`/`albums`/`songs` — legitimate collisions exist (two
  different artists can share a name). `tags` does get a hard
  `@@unique([normalizedName, category])` since it's a controlled vocabulary.
- **Partial release dates**: `releaseYear`/`releaseMonth`/`releaseDay` (all nullable) plus a
  `releasePrecision` enum, instead of encoding "unknown month" as `01`.
- **Soft delete**: `deletedAt` on `artists`/`albums`/`songs`/`tags`/`memories`/`festivals`/`playlists`.
  Join/personal-data rows (`song_tags`, `playlist_items`, `festival_performances`,
  `external_links`, `song_user_data`) are hard-deleted on removal, with an `AuditEvent` capturing
  `before_json` so the change stays recoverable from history. See ADR-0004.
- **`audit_events.entity_id` is plain text, not `@db.Uuid`**: most entities have a single UUID
  key, but composite-key rows (`song_tags`, `playlist_items`) need a compound `"id1:id2"` audit
  key, which isn't a valid UUID. This was a real bug in the initial implementation (attaching a
  tag or adding a playlist item 500'd) — fixed by widening the column, not by avoiding composite
  keys.
- **`audit_events` append-only** is enforced at both layers: `AuditService` is the sole write
  path and only ever calls `.create()`, _and_ a migration revokes `UPDATE`/`DELETE` on the table
  from the connecting role. See ADR-0004 for why that revoke is currently a no-op under the
  default local `docker-compose` superuser, but real once deployed against a non-superuser
  managed Postgres role.
- **Energy is numeric**, not a `Tag` row. See ADR-0007.
- **`song_analyses` is never updated in place** — a new analysis is a new row; approving/rejecting
  only flips `status`. This mirrors the source doc's rule 6.3 ("Neaktualizovat přepisem").
- **`memories.entityType`/`entityId` and `external_links.entityType`/`entityId` are loose
  polymorphic references** (no FK) since the referenced table varies by row.
